# المعمارية التقنية المقترحة — SIM

**الحالة:** تصميم أولي غير منفذ؛ أي تغيير جوهري يُوثق في سجل القرارات.

## 1. نموذج المكونات
```text
CLI (sim) ─────┐
               ├── Local API / IPC ── Recorder/Session Manager
GTK Desktop ───┘                         │
                                       ├── Collectors + Capability Probe
                                       │   ├── CPU/process/memory
                                       │   ├── Disk/network/filesystems
                                       │   └── Optional GPU/thermal/power/SMART
                                       ├── Sample Validation/Normalization
                                       ├── SQLite + Events + Session Export
                                       └── Analysis / Recommendations
```
CLI وDesktop واجهتان لخدمة جمع بيانات واحدة. يمكن لأوامر الاستعلام عن الجلسات السابقة قراءة مخزن البيانات دون تشغيل خدمة التسجيل.

## 2. الاختيارات المبدئية
- **لغة النواة:** Python 3.12 على Ubuntu 24.04، مع حزمة `psutil` وواجهات Linux /proc و/sys؛ يُفضَّل الحد الأدنى من الاعتمادات.
- **واجهة Desktop:** GTK4 + Libadwaita عبر PyGObject، مع فصل التصميم عن مصادر القياس.
- **الخلفية:** systemd --user على الأنظمة التي تدعمه، مع إمكانية إضافة مشغل بديل للتوزيعات التي لا تستخدم systemd.
- **التخزين:** SQLite للفهرسة والاستعلام والجلسات، وملفات تصدير مفتوحة JSON/JSONL. التصدير ليس مجرد نسخ عشوائي للقاعدة.
- **الأمان:** اتصال محلي بخدمة المستخدم، ملفات ومجلدات ضمن XDG مع أذونات مقيدة، وعدم مطالبة المستخدم بكلمة مرور root لتشغيل المراقبة الأساسية.

**ملاحظة:** هذه اختيارات تصميم لا إثبات لتوافق الحزم أو لنجاح تشغيلها على الجهاز المرجعي؛ التحقق جزء من المرحلة 0/1.

## 3. مصادر القياس والموائمات
1. مؤشرات عامة: psutil، و/proc/stat و/proc/meminfo و/proc/<pid>، و/sys.
2. GPU: اكتشاف DRM/Intel/AMD/NVIDIA؛ ربط الأداة أو الواجهة حسب العتاد والصلاحية. عدم دعم نسبة الاستهلاك لكل عملية أمر مقبول ومعلن.
3. الطاقة: مستشعرات البطارية وRAPL إن وجدت؛ لا نُسند واطًا دقيقًا للتطبيق دون أداة أو نموذج صالح.
4. صحة القرص: SMART إن توفر وبصلاحية مناسبة؛ تتجنب المسوحات المكلفة في دورة أخذ عينات سريعة.
5. الحرارة: lm-sensors/واجهات hwmon حسب التوفر.

كل موائم يعيد: `value`، `unit`، `source`، `availability`، و`sampled_at`. يجب ألا تعطل أخطاء موائم اختياري تسجيل CPU/RAM.

## 4. تجميع التطبيقات
نحتفظ بالعملية كوحدة أولية (PID مع زمن بدء العملية)، ثم ننشئ علاقة احتمالية بالتطبيق من desktop entry/cgroup/process tree/metadata حيث تكون متاحة. لا يجوز جمع RSS ثم الادعاء أنه «استهلاك RAM الحقيقي» للتطبيق عند وجود ذاكرة مشتركة. نكشف طريقة الإسناد وثقتها وموارد العمليات غير المصنفة.

## 5. دورة حياة الجلسة
1. `start`: تحقق من الحالة وتحديد مسار خاص بالجلسة ونسخة المخطط.
2. تسجيل معلومات الآلة/القدرات وأصل الزمن ومعدل العينة.
3. أخذ عينات دورية مع قياس التأخير والفجوات وإحصاءات كلفة المراقب.
4. مزامنة الكتابة دوريًا وتحديث ملخصات قابلة لإعادة البناء.
5. `stop`: إغلاق منضبط؛ إذا وقع انهيار تحتفظ الجلسة بحالة INTERRUPTED ويعاد استرجاع الفهرس دون اختلاق عينات.

## 6. استراتيجية الانتقال بين التوزيعات
الطبقة العامة لا تستورد أوامر Ubuntu بشكل مباشر؛ تعبئها موائمات لكل نوع من مصادر البيانات ومدير الخدمات والتغليف. أول حزمة .deb لاحقًا، ثم اختبار Ubuntu الأحدث والتوزيعات Debian/Fedora وغيرها كل بملف تحقق مستقل. لا تعني «Linux» أن كل المزايا متساوية على جميع الأجهزة.

## 7. خطوط الجودة
- type hints وlint وunit tests وintegration tests لطرق البيانات.
- synthetic fixtures لحالات PID reuse، العداد الذي يلتف، انهيار المستشعر، الوقت غير المنتظم، نقص الصلاحية، النفاد من التخزين.
- اختبار رجعي للرسوم والتقارير حتى لا تتغير تعاريف النسب بين الإصدارين.
- لا تبديل تلقائي للترددات أو إعدادات النظام أو إيقاف البرامج في مرحلة القياس.
